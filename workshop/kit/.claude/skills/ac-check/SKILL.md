# ตรวจความพร้อมเทสต์ของ acceptance criteria

## ข้อมูลที่ต้องมี
- user story และ AC (ไฟล์ใน docs/requirements/ หรือข้อความที่ผู้ใช้วาง)
- ถ้ามีเอกสารต้นทาง (ข้อความจากเจ้าของงาน) ให้อ่านด้วย เพื่อเทียบว่า AC ไม่ได้เติมสิ่งที่ต้นทางไม่ได้พูด

## ขั้นตอน
1. แยก AC ทีละข้อ ตรวจว่าแต่ละข้อเขียนแบบ Given / When / Then และวัดผลได้ (มีค่าที่ตรวจได้ ไม่ใช่คำอย่าง "เร็ว" "ง่าย")
2. ไล่ 4 ด้าน แล้วให้คะแนนด้านละ 0-25
   - **Happy path**: ทางปกติครบทุกบทบาทที่เกี่ยวข้องไหม
   - **Negative path**: ข้อมูลผิด ไม่มีสิทธิ์ สถานะไม่ถูก ทำซ้ำ มีข้อไหนบ้าง
   - **Boundary**: ค่าขอบ (0, ว่าง, ยาวสุด, เวลาตรงเส้น SLA, วันเปลี่ยนกะ) มีข้อไหนบ้าง
   - **Non-functional**: สิทธิ์, audit, ประสิทธิภาพ, ข้อความแจ้งผู้ใช้, การแจ้งเตือน
3. ทุกช่องว่างที่เจอ ให้เขียนเป็นคำถามถึงเจ้าของงาน ห้ามเติมคำตอบเอง
4. เสนอ test case ที่ควรมีสำหรับ AC ที่ผ่าน

## รูปแบบผลลัพธ์
```
คะแนนรวม: NN/100  (พร้อมเทสต์เมื่อ 80 ขึ้นไป และไม่มีด้านไหนต่ำกว่า 15)

| ด้าน | คะแนน | สิ่งที่มี | สิ่งที่ขาด |
|---|---|---|---|

คำถามถึงเจ้าของงาน
1. ...

test case ที่เสนอ
| รหัส | อ้าง AC | Given | When | Then |
```

## ข้อห้าม
- ห้ามแต่ง business rule ที่ต้นทางไม่ได้บอก ถ้าไม่รู้ให้เขียนว่า "ไม่ระบุ" แล้วตั้งเป็นคำถาม
- ห้ามให้คะแนนเต็มด้านไหนถ้ายังมีคำถามค้างในด้านนั้น
